# MS365 Copilotプロンプトジェネレーター 戦略計画書

## — Big4コンサルティングファームにおけるデリバリ活用のための設計・展開計画 —

---

## 1. エグゼクティブサマリー

本計画書は、Big4コンサルティングファームの中核業務である**提案活動・企画立案・リサーチ・プロジェクト推進（デリバリ）**の各場面において、MS365 Copilotを最大限に活用するための「プロンプトジェネレーター」を設計・展開するための戦略計画を定義するものである。

### 本取り組みの骨子

| 項目 | 内容 |
|---|---|
| 目的 | コンサルタントのドキュメント作成生産性を向上させ、アウトプット品質を標準化する |
| 手段 | 業務シーン別に構造化されたプロンプトを自動生成する「プロンプトジェネレーター」の構築 |
| 実行環境 | MS365テナント内で完結（SharePoint / Copilot Chat / Copilot Studio / Power Platform） |
| 制約条件 | 社内ナレッジリソースおよび外部Web検索は利用可。インターネットへのファイル送信・外部からのファイル取得は不可 |
| 展開方針 | 3フェーズ制（基盤構築 → パイロット展開 → 全社展開・高度化）、約9〜12ヶ月 |

### 期待効果（定量目標の例）

- 提案書・企画書の初稿作成時間を **40〜60%削減**
- リサーチサマリー作成のリードタイムを **50%短縮**
- 議事録・ステータスレポート等の定型ドキュメント作成を **70%自動化**
- ジュニア〜シニア間のアウトプット品質のばらつきを縮小（レビュー指摘件数で計測）

## 2. 背景と課題認識

### 2.1 Big4業務におけるドキュメント作成の特性

コンサルティング業務のアウトプットは本質的に「ドキュメント」である。業務時間の相当割合が以下の作成に費やされている。

1. **提案活動（Pursuit / BD）**: RFP分析、提案書、オリエン資料、見積根拠、Win Theme整理、競合ポジショニング
2. **企画立案（Planning）**: 企画書、構想書、事業計画ドラフト、ロジックツリー、施策オプション評価
3. **リサーチ（Research）**: 業界動向調査、規制・政策動向、企業分析、ベンチマーク、先行事例調査
4. **プロジェクト推進（Delivery）**: 議事録、ステータスレポート、課題管理表、ワークショップ設計、中間・最終報告書

### 2.2 現状の課題

| 課題 | 内容 |
|---|---|
| プロンプト品質の属人化 | Copilotの出力品質は入力プロンプトに大きく依存するが、良いプロンプトを書けるかは個人スキルに依存している |
| ナレッジの再利用不足 | 過去の優れた提案書・報告書が社内ナレッジに蓄積されていても、Copilot活用時に体系的に参照されていない |
| 出力品質のばらつき | 同じ依頼でもプロンプトの書き方次第で成果物の構造・粒度・トーンが大きく変わり、レビュー負荷が増大 |
| セキュリティ懸念による利用萎縮 | クライアント機密の扱いに対する不安から、Copilot活用が進まない、あるいは逆に不適切な入力が発生するリスク |
| 学習コストの高さ | プロンプトエンジニアリングの学習に時間を割けるコンサルタントは少なく、活用が一部に偏る |

### 2.3 解決アプローチ

「**個人がプロンプトを書く**」から「**ジェネレーターがプロンプトを組み立て、個人は業務パラメータを入力する**」への転換を図る。これにより、プロンプトエンジニアリングの専門知識をツール側にカプセル化し、全コンサルタントが一定水準以上のCopilot活用を実現できるようにする。

## 3. プロンプトジェネレーターのコンセプト設計

### 3.1 基本コンセプト

プロンプトジェネレーターとは、以下の3要素を組み合わせて、MS365 Copilot（Copilot Chat、Word/PowerPoint/Excel内Copilot）にそのまま投入可能な高品質プロンプトを生成する仕組みである。

```
[業務シーン選択] × [パラメータ入力] × [プロンプトテンプレート] → 完成プロンプト
```

**動作イメージ:**

1. ユーザーが業務シーンを選択（例:「提案活動 > RFP分析」）
2. 必要パラメータを入力（クライアント業界、提案テーマ、成果物形式、想定読者、トーン等）
3. ジェネレーターがテンプレートにパラメータを埋め込み、構造化プロンプトを出力
4. ユーザーがプロンプトをCopilotに貼り付け（または連携エージェントが直接実行）
5. 生成結果をレビュー・編集し、成果物として完成させる

### 3.2 プロンプト設計フレームワーク（6要素構造）

全テンプレートは以下の6要素で標準化する。この構造自体が本取り組みの中核IPとなる。

| 要素 | 内容 | 例 |
|---|---|---|
| ① Role（役割） | Copilotに与える専門家ペルソナ | 「あなたは製造業のDX戦略を専門とするシニアコンサルタントです」 |
| ② Context（文脈） | 案件背景・クライアント状況・制約 | 業界、企業規模、プロジェクトフェーズ、既知の論点 |
| ③ Task（タスク） | 具体的な作成指示 | 「RFPの要求事項を分解し、評価配点の高い順に対応方針を整理してください」 |
| ④ Reference(参照) | 参照すべき社内ナレッジ・Web情報の指定 | 「SharePoint上の過去提案書」「最新の業界レポートをWeb検索で確認」 |
| ⑤ Format（形式） | 出力構造・分量・成果物形式 | 「PowerPoint構成案として、セクション見出し＋各3行のキーメッセージ」 |
| ⑥ Quality（品質基準） | 品質チェック観点・禁止事項 | 「MECE性を担保」「出典を明記」「推測と事実を区別」「クライアント固有名は入力された情報のみ使用」 |

## 4. アーキテクチャ設計方針

### 4.1 制約条件の確認

| 制約 | 設計への反映 |
|---|---|
| 社内ナレッジリソース参照は可 | SharePoint / OneDrive / Teams上のナレッジをMicrosoft Graph経由でCopilotに参照させる設計を積極活用 |
| 外部Web検索は可 | リサーチ系ユースケースではBing経由のWeb grounding（公開Web情報の参照）を活用 |
| インターネットへのファイル送信は不可 | 外部SaaS型プロンプト管理ツールは採用不可。全コンポーネントをM365テナント内に構築 |
| 外部からのファイル取得は不可 | 外部データセットの直接取込は行わず、Web検索結果のテキスト参照に限定 |

### 4.2 実装アーキテクチャの段階的進化

**Stage 1: プロンプトライブラリ型（最速立ち上げ・ローコード）**

- SharePointリスト（またはExcel/Loop）でプロンプトテンプレートカタログを管理
- テンプレートはコピー＆ペースト用のパラメータ穴埋め形式（`{業界}`, `{テーマ}` 等）
- 分類・検索・利用ガイドをSharePointサイトとして整備
- 利点: 数週間で立ち上げ可能、ガバナンスが単純
- 限界: パラメータ埋め込みが手作業

**Stage 2: ジェネレーターアプリ型（フォーム駆動の自動組み立て）**

- Power Apps（またはFormsベース）でパラメータ入力UIを構築
- Power Automateでテンプレートとパラメータを合成し、完成プロンプトを生成・コピー可能に提示
- 利用ログ（どのテンプレートが何回使われたか）を自動収集し、改善サイクルに接続
- 利点: 入力ミス削減、利用状況の可視化、テンプレート改訂の一元管理

**Stage 3: Copilotエージェント型（プロンプト生成と実行の統合）**

- Copilot Studioで宣言型エージェント（Declarative Agent）を構築
- エージェントが対話でパラメータをヒアリングし、内部でプロンプトを組み立て、社内ナレッジ（SharePoint接地）とWeb検索を組み合わせて成果物ドラフトまで直接生成
- ユースケース別エージェント（提案エージェント、リサーチエージェント等）へ分化
- 利点: 「プロンプトを貼る」操作すら不要になり、業務フローに溶け込む

> 各Stageは置き換えではなく積み上げである。Stage 1のカタログはStage 3でもエージェントのナレッジソースとして機能し続ける。

### 4.3 ナレッジ接地（Grounding）設計

- **社内ナレッジ**: 過去提案書・メソドロジー・業界ナレッジを格納するSharePointライブラリを「Copilot参照用キュレーション領域」として整備。機密区分ラベル（Sensitivity Label）が適切に付与されたもののみ格納
- **外部Web**: リサーチ系テンプレートには「出典URLと取得日を必ず明記」「一次情報（IR・官公庁・業界団体）を優先」という品質基準を組み込む
- **アクセス制御**: Copilotの参照範囲はユーザー本人の権限に従うため、ナレッジ領域の権限設計をプロジェクト・部門単位で厳格化する

## 5. セキュリティ・ガバナンス設計

Big4としてクライアント機密を扱う以上、ガバナンスは機能開発と同等以上の優先度で扱う。

### 5.1 データ保護の原則

1. **テナント内完結**: プロンプト、入力データ、生成物はすべてM365テナント内に留まる。外部へのファイル送信は技術的にも運用的にも遮断（既存制約と整合）
2. **機密区分に応じた入力ルール**: クライアント名・非公開数値等の入力可否を機密区分ごとに定義し、テンプレート内に注意書きとして埋め込む（例:「本テンプレートには非公開のクライアント情報を入力しないでください」）
3. **Sensitivity Label / DLP連携**: 生成物にも自動ラベリングを適用し、既存のDLPポリシーの管理下に置く
4. **クライアント契約との整合**: AI利用に関するクライアント別の契約条件（AI利用禁止条項等）を確認できるチェックリストをジェネレーターの入口に配置

### 5.2 品質・責任の原則

1. **Human-in-the-loop必須**: Copilot出力はドラフトであり、成果物責任は作成者・レビュー者にあることを利用規程に明記
2. **ハルシネーション対策**: 全テンプレートのQuality要素に「事実と推測の区別」「出典明記」「検証必須項目のフラグ付け」を標準装備
3. **監査可能性**: Stage 2以降は利用ログを保全し、監査・インシデント調査に対応可能とする

### 5.3 利用規程・教育

- 「Copilot利用ガイドライン」をジェネレーター公開と同時にリリース
- eラーニング（30分想定）＋ハンズオン（ユースケース実演）をセットで提供
- 違反リスクの高い操作（機密情報のWeb検索クエリへの混入等）はテンプレート設計側で構造的に防止

## 8. KPIと効果測定

### 8.1 KPI体系

| レイヤー | KPI | 目標（Phase 3末） |
|---|---|---|
| 利用度 | 月間アクティブユーザー率（対象者比） | 60%以上 |
| 利用度 | テンプレート月間利用回数 | 継続的増加トレンド |
| 効率 | 初稿作成時間の削減率（自己申告＋サンプル計測） | 40%以上 |
| 品質 | レビュー指摘件数の減少率（対象成果物サンプリング） | 20%以上減 |
| 満足度 | ユーザーNPS / 継続利用意向 | NPS +20以上 |
| 安全 | セキュリティインシデント件数 | 0件 |

### 8.2 測定方法

- Stage 2以降の利用ログによる定量計測を基本とし、四半期ごとにユーザーサーベイで補完
- 「プロンプトジェネレーター利用群 vs 非利用群」の成果物作成時間比較をパイロット部門で実施し、効果のエビデンスを確保

## 9. リスクと対応策

| リスク | 影響 | 対応策 |
|---|---|---|
| クライアント機密の不適切な入力 | 重大（契約違反・信用失墜） | テンプレート内注意書きの構造化、DLP・ラベリング、教育、入口チェックリスト |
| ハルシネーションによる誤情報の成果物混入 | 高 | Quality要素標準装備、出典明記ルール、Human-in-the-loopの規程化 |
| 利用が定着しない（作って終わり） | 高 | チャンピオンネットワーク、成功事例の社内広報、業務フローへの組込（Stage 3） |
| テンプレートの陳腐化 | 中 | 月次改訂サイクル、利用ログに基づく棚卸し、現場からの改善提案窓口 |
| Copilot機能・ライセンスの仕様変更 | 中 | Stage 1のカタログ資産はツール非依存で維持、アーキテクチャの疎結合設計 |
| 過度な依存によるスキル空洞化 | 中 | 「プロンプトの構造を学ぶ教材」としてテンプレートを位置づけ、思考プロセスを可視化する設計 |

## 10. 成功のための戦略的ポイント

1. **小さく始めて速く証明する**: 最初の3ヶ月で6ユースケースに絞ったPoCを完遂し、定量効果を示すことが全社展開の政治的資本になる
2. **プロンプトは「ナレッジ資産」として経営管理する**: テンプレートカタログはファームのメソドロジーと同格のIPであり、改訂・版管理・品質責任を明確化する
3. **ガバナンスを推進の武器にする**: 「安全に使える仕組みがあるから使ってよい」というメッセージが、利用萎縮とシャドーAI利用の両方を防ぐ
4. **段階的アーキテクチャで投資リスクを制御する**: SharePointカタログ（数週間・低コスト）から始め、効果実証後にPower Apps・Copilot Studioへ投資を拡大する
5. **現場のトップパフォーマーを巻き込む**: 優秀なコンサルタントの暗黙知（提案ストーリーの組み方、リサーチの当たりの付け方）をテンプレートに転写することが品質の源泉となる

## 付録A: プロンプトテンプレートのサンプル（A-2: 提案骨子作成）

```text
【役割】
あなたは{業界}業界のクライアントに対する提案経験が豊富なシニアコンサルタントです。
経営層に響くストーリーライン設計を得意としています。

【文脈】
- クライアント: {業界}の{企業規模}企業
- 提案テーマ: {提案テーマ}
- クライアントの背景課題: {背景課題}
- 提案の競合状況: {競合状況（分かる範囲で）}

【タスク】
上記の文脈に基づき、提案書のストーリーライン（骨子）を作成してください。
以下のステップで思考を進めてください:
1. クライアント経営層の関心事を3つ仮説立てする
2. その関心事に応えるWin Themeを設定する
3. 「現状認識 → 課題の構造化 → 解決の方向性 → 提案内容 → 実行計画 → 体制・実績」
   の流れでセクション構成を設計する

【出力形式】
- PowerPoint構成案として出力
- 各セクション: セクションタイトル＋スライドタイトル案＋キーメッセージ（各1〜2行）
- 全体で15〜20スライド相当

【品質基準】
- キーメッセージは「So What?」に答える主張文で書く（体言止めの論点列挙は不可）
- 事実に基づく箇所と仮説の箇所を明示的に区別する
- クライアント固有の非公開情報は、上記【文脈】に入力された内容のみを使用する
```

## 付録B: 用語定義
